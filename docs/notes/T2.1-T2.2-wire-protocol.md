# T2.1 / T2.2 — The wire protocol

**Tasks:** `Frame`, `FrameType`, `FrameCodec` (4-byte length prefix + UTF-8 JSON header + optional
binary body), plus tests that specifically cover RFCOMM stream quirks.

## Wire format

All lengths big-endian, `uint32`:

```
[4] payload length  = 4 + header length + body length
[4] header length
[n] UTF-8 JSON header  (a FrameHeader)
[m] binary body        (empty except PICTURE and FILE_CHUNK)
```

Twelve frame types, named exactly as the UML names them, and serialised **by name**
(`JsonStringEnumConverter`) rather than by number: a packet trace reads as `{"t":"TEXT",...}` and a
build that adds a frame type cannot silently renumber an existing one. A frame carrying a type name
this build does not know is rejected as corrupt rather than mis-parsed.

## Files

| File | Role |
| --- | --- |
| `Transport/FrameType.cs` | The twelve frame types, each documented with who sends it and why. |
| `Transport/FrameHeader.cs` | One record covering all twelve types; every field optional and omitted from the JSON when null, so a chat line stays ~90 bytes. |
| `Transport/Frame.cs` | `Frame` = header + body, twelve factories, and the mapping to/from `Domain` messages. |
| `Transport/FrameDecoder.cs` | Push parser: bytes in as they arrive, whole frames out. This is where every stream quirk is absorbed. |
| `Transport/FrameCodec.cs` | `Encode`, `WriteAsync`, `ReadAsync`, and `ChunkAsync` for file transfer. |

## Decisions

1. **Length prefix outside the payload, header length inside it.** The outer prefix answers "how
   many bytes must I wait for before there is a frame at all"; the inner one answers "where does the
   JSON stop". With only the outer prefix a receiver would have to scan for a `{`/`}` boundary, and
   `}` is a byte that can legitimately appear inside a binary body.
2. **The binary body is raw.** A picture's bytes go in `Frame.Body` untouched — no base64 (a third
   more bytes over a link that does ~200 KB/s at best, plus a copy at both ends).
   `ABinaryBodyIsSentRawNotBase64` asserts the actual byte sequence appears contiguously in what was
   encoded.
3. **Two read paths, one set of rules.**
   * `FrameDecoder` is push-based: `Append(bytes)` then `TryNext(out frame)`. Used by anything with
     its own buffering, and it is what the quirk tests drive directly.
   * `FrameCodec.ReadAsync(stream)` is pull-based and reads **exactly one frame**, stopping at the
     frame's last byte. That makes it safe to call in a loop with no state at all: any leftover bytes
     simply stay in the stream for the next call (`ReadingFramesFromAStreamKeepsItsPlace`). Both
     paths share the same constants and the same error type.
4. **The peer's length is never trusted.** The prefix is attacker-controlled, so it is range-checked
   before a single byte is allocated: below `HeaderLengthBytes` or above `MaxFrameBytes` (8 MB) is a
   `FrameException`, and a header length running past its own frame likewise. This is the
   "corrupt frame received" case from T6.1, handled before M6.
5. **A clean close between frames is not an error.** `ReadAsync` returns `null` when the stream ends
   with zero bytes read at a frame boundary, but throws `FrameException` if it ends *inside* a frame.
   A read loop can therefore tell "the peer closed the connection" from "the peer crashed
   mid-message".
6. **A message keeps its id.** `Message` constructors take an optional `id`, so the receiver's
   `TextMessage` has the sender's `Guid`. Two processes can then recognise the same message, which
   de-duplication and later acks depend on.
7. **`FileMessage` maps to `FILE_META`, not to a body.** The announcement carries name, size and
   `TransferId`; the bytes follow as numbered `FILE_CHUNK` frames and end with `FILE_DONE`. So a
   20 MB file never has to exist in memory on either side — `ChunkAsync` streams it in 8 KB slices
   and yields `(Sequence, Bytes)`.
8. **Chunk size is 8 KB**, not "as much as will fit": the server interleaves chat frames between
   chunks, so one large file must not starve a room of its conversation.

## What the tests pin down (T2.2)

`FrameCodecTests`, 24 tests:

* every frame type round-trips, byte for byte, header and body;
* empty body stays empty; a 700 KB body survives intact;
* a frame arriving **one byte at a time** still yields exactly one frame;
* **two frames in a single read** both come out, in order;
* **every split point** of a frame — inside the length prefix, inside the header length, in the
  middle of the JSON, between header and body — is swept (`for split in 1..len-1`), asserting that
  nothing decodes early and the full frame arrives afterwards. Boundary handling is therefore not
  special-cased anywhere;
* `DribbleStream`, a `Stream` that returns at most one byte per `ReadAsync`, proves `ReadAsync`
  loops instead of trusting a single read;
* a mid-frame close is an error, a between-frames close is null;
* corrupt input — oversized length, header length past the frame, non-JSON header, unknown frame
  type — is refused with `FrameException` and without a large allocation;
* domain mapping: `TextMessage` ⇄ `TEXT` (id, sender, room, body, timestamp all preserved), picture
  bytes ride in the body, `FileMessage` → `FILE_META` with its `TransferId`, join notices →
  `SYSTEM_NOTICE`, and non-message frames map to `null`;
* `ChunkAsync` on a 2-chunk-plus-remainder file yields sequences 0,1,2 with no byte lost or
  duplicated; an empty file yields no chunks at all.
