# T5.4 — an incoming file, in the window

Milestone M5 · task T5.4 · area UI

## What the task asked for

The receiver side of F8: an incoming-file notice, a pick-a-folder dialog, a progress indicator per job, and
the save on completion.

## What was there before

`ChatForm.ReceiveFile` — written at T0.5 as a placeholder — put up a modal `ConfirmDialog` ("Accept it?")
and then a `SaveFileDialog`. Two problems, both of which show up the moment more than one file is moving:

* **A dialog stops the room.** While the box is up the person cannot type, cannot read what arrived while
  they were deciding, and cannot do anything else with the window. A file over Bluetooth takes minutes; a
  modal question that lasts minutes is a wall.
* **Only one dialog can be up.** With two files arriving, the second offer has nowhere to be written down, and
  the answer to the first is a `DialogResult` on a stack that is already holding one.

It also asked for a *file name* (`SaveFileDialog`) rather than a place to put things, which is the wrong
question when three files arrive in the same minute.

## Now

**An offer strip.** A panel under the menu, shown only while something is being offered: who is sending,
what it is called, how big it is, and `Save to…` / `Decline`. The window stays live behind it. If a second
file is offered, the strip says `… - 1 more waiting`, and answering the first brings up the next.

The bytes keep arriving whether or not anybody answers, because they are already on the wire — so a strip
that disappears is not one that stopped the transfer, and `Decline` throws away the spool and tells the
sender, which is the transfer layer's job rather than the window's (`job.CancelTransfer()` is the whole
decline).

**A folder, not a file name.** `AskForFolder` is one virtual method over `FolderBrowserDialog`; the file keeps
its own name inside the chosen folder. Closing that dialog without choosing is *not* a refusal: the offer
stays up and the bytes keep coming, so a person who pressed `Escape` by accident has not lost a file they
meant to keep.

**One bar, both directions.** A `ToolStripProgressBar` in the status strip, with a label naming the file, the
percentage, `, saving` once this window has agreed to keep it, and `( +1 )` when others are moving too. The
same bar serves a file being sent: "how far has it got?" is the same question either way, and two bars would
be two things to look at for one question.

The bar is *read* from the jobs rather than driven by their progress callbacks. A chunk is 8 KiB, so a 100 MB
file is twelve thousand reports; a 250 ms poll produces the same picture, cannot arrive on the wrong thread,
and cannot be the reason a transfer waits. `FileTransferJob.Progress` is left for whoever wants the exact
number; this window has the approximate one and a timer.

**Saving waits for the file.** `SaveReceivedFileAsync` is called as soon as a folder is chosen and returns
when the file has been written — which for a file still arriving means when the last of it turns up. Nothing
is on disk before that. A test caught the fake service being better than the real one here: it used to write
the file the moment it was asked, which let a window report `saved` for a file that had not finished arriving.

## Two things the tests found in the window itself

* **Declining left the bar up.** A bar sitting at 3% of a file that had just been thrown away is a bar telling
  a lie. `Decline` now refreshes the bar as well as the strip, so it goes in the same click rather than up to
  250 ms later.
* **A stopped transfer left its offer on screen.** When the sender gives up, the strip has to come down with
  the transfer; a `Decline` button pointed at a file that no longer exists is a button to nothing.

## What the window shows in the transcript

The `[file] notes.txt (4,096 bytes)` line is written when the file is **announced**, not when it arrives, and
with the `MessageId` that came in `FILE_META`. The sender's window wrote that line at the same instant, and a
room whose transcript reads differently in different windows is a room where two people cannot afterwards
agree about what happened.

## Tests

`src/Lantern.Tests/IncomingFileUiTests.cs` (10):
offered without taking the window over (typing still works, transcript line already written, nothing saved) ·
declining throws the bytes away and stops them counting · a chosen folder gets the file only when all of it
has arrived · no folder chosen keeps the offer where it was · the bar shows how much has arrived, and goes
when it is over · stopping a file takes the bar away · two files arriving at once are offered one after the
other, with one bar saying there are two · a file stopped halfway says so and saves nothing · the offer comes
down when the sender gives up · a file sent from this window uses the same bar.

The fake service grew to make these possible: `FilesCompleteImmediately` (a fake that always finishes a file
cannot show a progress bar), `AdvanceFile` (bytes arriving, in either direction), `SimulateFileStopped` (the
`FILE_CANCEL` frame arriving) and `SaveRequests` (what the window asked for, seen from this side).

377 tests in the suite.
