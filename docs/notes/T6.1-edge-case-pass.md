# T6.1 — the six ways a room stops being tidy

Milestone M6 · task T6.1 · area Core (with UI)

An edge-case pass is not "write more tests". It is a list of things the happy path never expects, asked one at
a time of the code that has to answer them. Six were named; all six now have a test in
`src/Lantern.Tests/EdgeCaseTests.cs`, and four of them turned out to have a hole in the product behind them.

## Radio off

Asked of the *window*, not the transport: a person switches Bluetooth on and presses "Start server" anyway.
`StartupForm` already had the catch and the sentence (`could not host: …`), and nothing had ever pressed that
button on a machine that says no — which is the classic state of a handled case that nobody has checked. Now
`HostingWithoutARadioIsToldInWordsAndTheWindowIsStillThere` runs the real startup window over a factory whose
server throws the radio's own words, and asserts the bar says it, that there is no dialog to dismiss, and that
both doors (host again, scan) are still open — because the same person who plugs the dongle in tries again from
where they are standing.

Scanning without a radio was already covered (`ARadioThatWillNotInquireStillLeavesThePairedList`, M4).

## Walks out of range mid-transfer — two bugs, one test each

The server side was sound: when a connection goes, `ForgetTransfersOf` stops what it was sending and marks it
declined for what it was receiving. The client side was not.

**A file arriving when the connection goes used to stay unfinished for ever.** `FileReceiving.AbandonUnfinished`
has existed since T5.3 and was *never called from anywhere* — grep says so. And when the read loop ends on its
own (which is what "out of range" means), it does not go through `DisconnectAsync` either, so the first attempt
at fixing this in `DisconnectAsync` changed nothing at all; the test is what found that. Now the read loop
abandons unfinished transfers itself, whoever ended the connection, and
`AFileArrivingWhenTheConnectionGoesIsGivenUpRatherThanCountedForever` asserts the job ends, is marked stopped,
and leaves no `.part` in the user's incoming folder. Left alone, that spool is found next month.

**A window said "sent" about a file that never arrived.** `ChatForm.FileFinished` decided its status line from
"the transfer ended", so a transfer that ended *broken* — the link died halfway, and the transfer layer had
already said so in a line of its own — was followed by "holiday.zip sent". It now asks whether the transfer was
`IsComplete`, and says `holiday.zip did not finish` when it was not. `SendingAFileOverAGoneConnectionEndsTheJobRatherThanHanging`
covers the other half: pressing Share on a connection that has gone must end the job with a sentence, not hang
a bar at 0 % on a thread that is waiting for a socket nobody owns. (A refusal in words at the moment they press
is also an acceptable answer, and the test accepts either — what it will not accept is a transfer that never
ends.)

## Corrupt frame received

`FrameCodecTests` has always refused garbage at the codec, and `AConnectionThatNeverIntroducesItselfIsDroppedWithoutANotice`
has always dropped a silent connection. What had never been asserted is the *room's* stake in it: that the one
connection that spoke nonsense is the one that ends. `GarbageOnTheWireEndsOneConnectionAndLeavesTheRoomAlone`
writes raw bytes down a loopback socket, reads until that connection is finished with, and then proves the room
is untouched — the room still open, another member still talking, the host still able to edit rooms.

## Host deletes the room a client is typing in

Core had it (`DeletingARoomTellsThePeopleInsideAndPutsThemNowhere`). The typed half of it was the window's
business: `ARoomClosedUnderSomeoneWhoseMessageIsHalfTyped` types a sentence, has the room deleted underneath it,
and asserts the words are still in the box, the window noticed, Send is greyed rather than waiting to fail, and
pressing the greyed button changes nothing. A room went away; a person's sentence did not.

## Send while disconnected

`TalkingAfterTheConnectionGoesIsRefusedInWords`: text and picture both come back as a sentence
("Connection lost.") promptly rather than a hang. This had been true in the code since T2.5 and untrue in every
test until now.

## Duplicate nicknames — the one where the obvious rule was wrong

I started by refusing them: a second `Cara` joining a room that already has one got an `ERROR` frame saying
"Choose a different name to join", and two tests said so. Then the full suite produced
`MultiClientHostTests.TwoPeopleWithTheSameNicknameAreStillTwoPeople`, written in M4, which asserts the opposite
— and that test was right and I was.

The reason is not in the server, it is in the door. A nickname is chosen once, on the way into the program, and
there is no way to change it from inside a room. So refusing a second "Alex" does not resolve the clash, it
strands a person outside the room they wanted with nothing they can do about it — and the sharpest version of
the case is somebody whose name happens to be the host's machine's name. Turning them away is a rule the
program cannot help anybody follow.

What the clash actually costs is legibility: two lines attributed to "Alex" are two people, and nothing in the
transcript says so. So the room is told instead, at the moment it becomes true:

```
cara - there are 2 people in this room called cara
```

— a system notice like any other (F11), in every window in that room including the first Cara's, which is the
window most in need of knowing that the next "Cara" on screen may not be the one it was answering. The count is
case-insensitive, because `cara` and `Cara` read identically to anybody looking at a list. The rule is per room
and no wider: two Caras in two rooms are nobody's problem, and `TheSameNameInTwoDifferentRoomsIsNobodysBusiness`
checks that Room 1 hears nothing about the Cara in Study.

Two things came out of the abandoned version that are worth keeping, so they are tested in their own right: a
refusal of *any* join now also sends an empty member list, because a client writes the room it asked for into
its own state straight away (the answer is nearly always yes) and a refusal that only said "no" in a status line
leaves a window showing a room it is not in, with a Send button waiting to fail; and the `User` doc comment no
longer promises that a shared name is nobody's business.
