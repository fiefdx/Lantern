# T7.1–T7.3 — the group window grows up (headline over every message, a photo you can look at, rooms from the menu)

Asked for in one sentence, and all of it is one window:

> host need rooms creation/deletion functions, in group context, every message should a headline include message
> datetime and user name, then the message content start a new line, headline and content should has different
> color, image/picture content should support double click it popup a large window to show the image, the image
> render window should support image scale operations.

Three features (F13 layout, F14 picture viewer, F5 room menu), one file in the middle of all of them
(`ChatForm`), and one thing they share: **the transcript is not a list of lines any more.** That is what made the
interesting decisions.

---

## F13 — a headline, then the message

A message is now drawn as

```
[2026-03-07 14:05] User 2      ← dark blue
the part I typed               ← the window's own text colour
```

**Why the split.** In a room with four people, a line that carries the name, the time and the text is a wall: the
names sit in the middle of every line, nothing lines up, and the eye cannot find who said what. A group chat is
read as a log, and a log has the meta-information on its own line. Two colours so the scaffolding is visibly not
the message: the parts that are always there (when, who) recede and what somebody typed stands out.

**Why the date.** `HH:mm` cannot answer "when did that arrive?", which is exactly the question a chat that has
been open since the morning produces. It costs eleven characters.

**Why one class.** `TranscriptStyle` decides the shape; `ChatForm` paints it. The transcript is drawn for typed
messages, pictures, files, join/leave notices and the welcome line nobody sent — and it is **rebuilt from a room's
history** every time somebody switches rooms. A rule repeated in four places is four rules, and the rebuild was
the one that would have drifted first.

**Notices are shaped the same and coloured quieter.** `[time]` with no sender (nobody sent it, so there is no name
to invent) and grey content, because "User 3 joined" is not somebody speaking to the room. Still two different
colours: the shape of an entry does not change from message to message, so one rule can be read at a glance.

**How it is tested.** The colour is read back **out of the window** — select a run of text in the `RichTextBox` and
ask `SelectionColor` — rather than by parsing its RTF and guessing which `\cf` applies where. Two things fell out
of doing it that way: `SystemColors.WindowText` and `Color.Black` are the same colour wearing different names, so
colours are compared by value; and the newline between headline and content is painted in the **content's** colour,
so copying an entry out of the transcript does not carry a stray blue line break.

What was got wrong first: a test that asserted a rebuilt transcript is *identical* to the live one. It is not, and
correctly so — leaving a room is announced, so coming back to it shows an entry that was not typed (F11). The
assertion is now per message: this line sits directly under the headline of the person who sent it.

## F14 — a photo opens in a window you can scale

`PictureViewerForm`: opens over most of the screen, fitted to it, and then whatever size the person looking
decides — **−** / **+** buttons, the mouse wheel, `+` / `-` / `0` (own pixels) / `F` (fit) / double-click the photo
(toggle), and the scale read out as a percentage because the question anybody asks is *at what size am I looking
at this*.

Four decisions worth their ink:

* **Looking at a picture writes no file.** It used to: save the bytes into a folder in app data and hand the path
  to the system photo viewer. That is two surprises — a file nobody asked for, and a window that is not this
  program's — sitting on the path of a double click, when the bytes are already in the message in memory. Getting
  the file out is still possible and is now something the person asks for: **Save to…** (Ctrl+S), one button, and a
  test that compares the folder before and after and asserts nothing appeared.
* **Fit never enlarges.** A 400 px photo stretched across a 1900 px window is the same photo with four times as
  many invented pixels. The default should be the honest one; the button is there for anybody who wants the
  interpretation.
* **The control is stretched, the bitmap is not resized.** A 4000 × 3000 photo at 800 % is a 32000 × 24000 bitmap
  — a gigabyte spent on one eyelash, and the wheel stops being usable. Scaling the drawing costs nothing per step.
* **One window per photo, owned by the chat window.** Double-clicking the same photo three times raises one window
  rather than stacking three; two photos are two windows (that is how you compare them); and closing the chat
  closes the photos, because a window out of a chat that no longer exists is nobody's. Owned, not modal: the room
  keeps talking while the photo is up, which is the normal case — a photo arriving in a group is usually followed
  by three messages about it.

`PictureMessage.ToImage()` is the domain's side of it: the photo at its own size, as **a copy that owns its
pixels**. `Image.FromStream` keeps reading from its stream while the image is drawn, so an image handed out over a
closed stream is a bomb with a delay — and a photo window is exactly the thing that draws it later, on a repaint,
when the message that carried it is long gone. There is a test that draws the image after the loader has been
disposed, because that is the only way to know the copy really is a copy.

The window has a parameterless constructor like every other window here, so it opens in design view — and
`DesignTime.Picture` hands it a picture made on the spot (a blue rectangle with a word in it) rather than an empty
grey box, because a layout cannot be judged against nothing. Outside the designer that constructor throws: a
window showing a photo nobody sent is the same mistake as a window showing a chat nobody joined.

## The double click, now that a line is not a message

Until F13, a picture in the transcript was one line and `openable` was a dictionary from that line's text to the
message — which is what a double click could be answered with, since the click knows the text under the caret and
nothing else.

After F13 that is unsolvable by text:

* an entry is three lines (headline, caption, thumbnail) and only the caption names a file;
* the headline is the *same text* for every message from that sender in that minute — so a text message and a photo
  side by side collide in the dictionary, and the wrong photo opens;
* the thumbnail is part of the entry and says nothing at all.

So each picture records the **character span** it was written into, and a click asks which span contains the caret.
Positions rather than line numbers, because positions also survive word wrap: narrow the window and the same text
has more lines, and a transcript that opened the wrong photo after somebody resized the window is a transcript that
opened the wrong photo. Two consequences a test pins down: the headline and the thumbnail open the photo too
(anywhere on the entry is the entry), and a caret that falls on nothing opens nothing — there is deliberately no
fallback to "the nearest picture", because a photo that opens itself is worse than a double click that did nothing.

## F5 — rooms made and unmade from inside the group

The host already had **New** and **Delete**, as two small buttons in the room list's header, and the Edit menu had
only **Rename room** — so the room you are standing in was the one room the menu could not do anything about.

Edit now reads **New room** (Ctrl+N), **Rename room**, **Delete room** (Ctrl+D), and both windows show all three,
with a client's greyed. The menu items call *exactly* what the buttons call — one implementation of "make a room"
and one of "destroy this one", so the two doors cannot drift apart into two behaviours.

* **Creating a room walks the host into it.** A room the host made and did not enter is a room with nobody in it,
  and the host would have to click it as well; a feature whose second step is obvious has an extra step. Going back
  is one click on the room they came from, and an empty room is empty, not damaged.
* **No right-click menu on the room list**, though it is what a person expects. In this window **a selection is a
  request to join** — that is the load-bearing fact behind the room-list re-entrancy crash
  ([room-list-re-entrancy.md](room-list-re-entrancy.md)), where a redraw that read as a click looped join → room
  list → join until the process died of a stack overflow. A context menu that acts on the row under the cursor
  needs a highlight that is not where the window is, and the highlight is the window's promise about itself. Not
  worth it for a menu that duplicates the Edit menu.
* **No shortcut takes an unmodified key.** A menu shortcut eats that key from whatever has the focus, and the
  message box is next to this menu — so `Del` stays the typing key, and the test asserts every shortcut on that
  menu carries a modifier.
* **Deleting the room you are in** leaves the window nowhere: no room, box and Send disabled (F6), and the
  transcript says *select a room* rather than going blank — a window that can't send to anything explains what
  would let it.

## The test harness was reporting passes for stuck tests

Writing these tests found it: `Sta.Run` started the UI body on an STA thread, waited thirty seconds, and returned
**whether or not the thread had finished**. A test sitting in front of a modal dialog nobody was going to click —
which is exactly what closing a `HostForm` does, since a host asks before it quits and disconnects everybody — looked
identical to a test that worked. Two of the new tests were "passing" that way, at 30 s each, in a suite that used to
take 48 s.

`Sta.Run` throws `TimeoutException` now. The rest of the suite was already clean, which is the reassuring part: it
had not been hiding anything else. The rule for the next person is the one the existing suites already follow —
dispose a window in a test, and override the asking when the test is *about* closing it
(`ClosingTheChatWindowTests`).

(colours on a projector, a message with line breaks, copying an entry out into Notepad), looking at a photo (every

`RoomManagementUiTests`, `PictureMessageTests` and `DesignViewTests` — 492 in the suite.

Wire unchanged: nothing in `Core/`, `Transport/` or `Storage/`. A v1.1 host still needs a v1.1 client (as since
v1.0.2, for reasons of room identity — see [room-identity.md](room-identity.md)), and nothing more.
