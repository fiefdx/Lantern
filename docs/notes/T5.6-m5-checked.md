## Two things that were wrong, found by asking the window rather than the wire

**1 · A folder that refused the file lost the file.** The receiver's save catches what the disk says and puts
one line in the status bar — and that was all. The offer strip had already come down when the folder was
chosen, so there was no way left to try another folder: "that share is read-only" meant "send it again", even
though every byte was still sitting in Lantern's own spool. An offer that cannot be answered twice is a file
lost to a typo.

The code comment even claimed the person "can pick a different folder and try again", which is the sort of
comment that is written about intention rather than about code.

Now a refused save puts the offer back up, and the test walks the whole recovery: folder that will not have it
→ told → asked again → same file lands in a folder that will, with the sender having sent nothing twice.

**2 · A file that arrived while nobody was answering had vanished from the screen.** The strip's queue was
pruned of any transfer that had *finished* — but a file that arrived whole and was never answered is exactly
the one still worth offering: the bytes are here, and the person never got to say where they go. Pruning is now
only for cancelled transfers. `AFileThatArrivedWhileNobodyWasAnsweringIsStillOffered` covers it, including
answering late and the file still being there to be had.

Same root cause, smaller: `FileFinished` announced "notes.txt arrived" for a file the window had already
accepted and was in the middle of saving. Both orderings of those two lines are possible, which made the
"saved notes.txt" assertion flaky on a loaded machine — and reading the window, "arrived" *after* "saved" is
the story told backwards. A file this window agreed to keep now says nothing on arrival; the line about it is
written when it has been written.

## One case nobody had thought of, which M6 would have caught

**A file name that is a path.** `FILE_META` carries a name string written by a stranger. The receiver keeps
`Path.GetFileName` of it, and the window builds the save path by combining that name with the folder the person
chose — so if the name were `..\..\elsewhere\payload.bin`, or `C:\Windows\payload.bin`, a receiver would be
letting the sender decide where its own disk gets written. The behaviour was already right and untested, which
is the dangerous combination.

`ANameWithAPathInItArrivesAsAFileName` is a theory over four announced names — a Windows relative path, an
absolute Windows path, a POSIX path, and a name padded with spaces — and asserts that what arrives is called
`payload.bin` in all four cases and lands where the receiver pointed.

## Checked against the exit criterion, and what only a person can check

> *"scenario 4 with pictures + scenario 5 fully work; sound plays on receive."*

Three things a test on one machine cannot assert, which is why `docs/testing/m5-manual-checklist.md` exists
(23 steps, loopback steps 1–19 and the radio steps 20–23):

* **Is the thumbnail legible, and is it a thumbnail?** `PictureTranscriptUiTests` can assert that a picture was
  embedded in the RTF; whether a person can tell what the photo is of, and whether the transcript grew a
  two-foot line, is a pair of eyes.
* **Are the two sounds two, and are they audible in the room?** The tests assert *which* cue was asked for;
  that a person can hear it over a lab, and that the file sound is distinguishable from the message sound
  without looking, is not testable from inside the process.
* **Does 12 MB survive a real radio?** Over loopback, a dozen megabytes is a memory and framing test. Over
  Bluetooth RFCOMM it is the actual claim of F8, at the actual rate, with somebody walking out of range
  halfway through (step 23): the transfer must stop and say so, and the half file must not be left in the
  chosen folder with the real name on it.

The checklist also keeps the two counters the report will want: the byte size on each machine after step 10,
and the elapsed time of step 20.
