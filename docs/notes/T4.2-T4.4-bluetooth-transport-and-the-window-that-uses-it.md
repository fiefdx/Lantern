## T4.2 — `BtRfcommServer`, `BtRfcommClient`, with the radio behind a seam

`IBtServer`, `IBtClient` and `IClientLink` again — the same three interfaces `ChatServer` and `ChatClient`
already hold — are implemented over RFCOMM. `FrameCodec` is untouched and `ChatServer` needed no change at
all: the point of T2 was that the engine does not know what it is talking over, and this task is where that
is either true or not.

**The seam.** `IRfcommListener`, `IRfcommConnector`, `IDeviceFinder` and `IRfcommConnection` sit between
Lantern and 32feet.NET. `ThreeFeetRfcommListener`, `ThreeFeetRfcommConnector`, `ThreeFeetDeviceFinder` and
`ThreeFeetRfcommConnection` — the only four classes in the application that reference 32feet — are in
`BtRfcommClient.cs` together, which makes "what do we actually know about this library" one file to read
rather than four to find.

The seam exists because of the measurement in T4.1: **one machine cannot be both ends of a Bluetooth
link**, so no test can drive a real RFCOMM pair, and a suite of 45 untestable classes would be a suite of
0. What is tested is everything Lantern decides for itself:

| Decided by Lantern, therefore tested | Where |
|:--|:--|
| What counts as a Bluetooth address | `RfcommAddressTests` — twelve hex digits, in the shapes Windows and the Settings app write them |
| What the accept loop tells the server, and what `Stop()` does to open links | accept loop hands over a link, `Stop()` drops every one of them and unregisters the service, a channel arriving into a shutting-down host is closed rather than handed up |
| How long a join attempt is waited for, and what each way of failing is called | own timeout above the stack's five seconds, socket codes → four sentences, cancellation stays a cancellation |
| Who a scan may list | paired + inquiry, deduped, never the machine doing the looking, unnamed devices listed by address, capped, partial results kept, a throwing stack kept out of the way |

`StreamLink` is the `IClientLink` over two streams and whatever `IDisposable` made them. It needed
creating because the link promises are testable nowhere else: closing twice must be one `Closed` event, and
the radio handle must not outlive the link.

**The synchronous `Connect`, on a worker thread.** `ConnectAsync` in 32feet 4.2.5 fails instantly with
WSAEINVAL (T4.1), so `Task.Run(() => client.Connect(endpoint))` is raced against Lantern's own timeout. The
abandoned dial's exception is observed deliberately: an unobserved exception on a thread-pool task is a
crash waiting for a finaliser, and the abandoned dial's `BluetoothClient` is disposed so the socket goes
with it.

**`Stop()` removing the SDP record matters as much as closing the socket.** A machine still advertising
Lantern after its host quit makes the next visitor's failure look like the visitor's fault.

**What is *not* covered, said plainly:** the four `ThreeFeet*` classes. They are exercised by hand through
`tools/BtSpike` and walked through in `docs/testing/bluetooth-pairing-how-to.md`. A test suite that
pretended to cover a radio would be worse than one that admits it cannot.

## T4.3 — discovery that reaches the join list, and the hosts it has to remember

`ServerBrowser.DiscoverAsync` was already transport-agnostic (T2.6 left an `IBtClient` parameter for
exactly this), so T4.3's work was the two things that make the list useful:

**An address a person can type.** `TryParseAddress` now reads a Bluetooth address in the shapes it is
written in, checked **before** a colon is read as a port separator. That ordering is the whole fix:
`f8:e4:e3:f9:60:3b` used to be rejected with `"3B" is not a port number`. A half-grouped paste
(`F8e4 E3-f9:603b`) is refused rather than cleaned up into something dialable — quietly trimming junk is
how a person ends up dialling the wrong laptop. The trade is in a test on purpose: a machine whose name is
exactly twelve hex digits is read as an address, because a paste from Settings is what a person is actually
holding.

**Machines joined before** (`Storage/JsonKnownHostsStore`, `%LOCALAPPDATA%\Lantern\known-hosts.json`, last
ten, most recent first). This file exists because of a measurement, not a feature request: a Windows host
is paired but not discoverable, so the machines worth offering are mostly the ones this laptop has joined.
Same discipline as the rooms file — atomic rename, unreadable file means *no history* and never an
exception, writes chained and flushed by `SavesCompletedAsync`, a failure reported through `SaveFailed`
rather than thrown at a join that has already succeeded. Addresses are normalised on the way in, so one
laptop is not three lines two of which fail.

`Merge` order: what answered first (fresher evidence a machine is in the room), then what is remembered,
each machine once, and a remembered machine that also answered keeps the name its radio reported today. A
stopped scan still returns the remembered list — the scan was stopped, not the question. Nothing is
filtered out for being a keyboard or a loopback address: every line shows an address and a person decides
which line is the friend.

## T4.4 — which transport a run uses, and the startup window using it

**`Core/Transports.cs` is the one place that reads the world.** `TransportWanted` has three answers because
a person can mean three things: `Auto` (radio if there is one), `Bluetooth` (radio, and hear about it if
there isn't), `Loopback` (this machine alone). `--loopback` beats `LANTERN_TRANSPORT`, and
`LANTERN_TRANSPORT=bluetooth` means *do not fall back* — being moved onto loopback with an empty list and
no mention of the radio is how a machine gets blamed for its driver. `Auto` with no radio falls back to
loopback and **says so in the status bar**, because the window has to open on any laptop (F9's rule,
applied one level up).

That changes how the manual checklists are walked through: two windows on one machine now need
`dotnet run --project src/Lantern -- --loopback`, and both checklists say so.

**The startup window** (`UI/StartupForm.cs`) now builds everything through an `ITransportFactory` it is
given, and takes it (plus an optional `IKnownHosts`) in a second constructor — the same seam as the dialog
seams in M3, for the same reason: a test can hand the window a fake radio.

- The transport is stated in the status bar **before anything is clicked**. A machine on loopback will
  never find a chat, and the status bar is the only place that can say why.
- **Scan is its own cancel.** The figure has no Stop button and none was added: the button that started the
  scan says "Scanning…" and is the one that stops it. An inquiry that never returns is the normal case for
  a friend whose machine is switched off.
- Busy means greyed out + wait cursor + the button's own text. No progress bar: the figure has nowhere for
  one, and the three things a person can see already say what is happening.
- An empty scan names the two reasons it is usually empty ("hosting… paired?") rather than saying nothing.
- A chat that answered is remembered; a chat that did not answer is not, because the next join list is
  short enough without lies in it.
- A failed join leaves the row selected and Join enabled — the friend's switched-off laptop should not make
  the person choose the row again.
- `ShowChat` is `protected virtual` so a test keeps hold of the window that was built. The alternative is
  `Application.OpenForms`, one list shared by every test class running in parallel, whose entries then have
  to be closed — and a chat window asks before it closes.

## Open questions taken forward

- **A field-test join path for a machine that is neither paired nor in the known-hosts list.** F2/F3 do not
  require manual address entry, and the figures have no box for it, so nothing was invented; but
  `TryParseAddress` supports it and `SetStatus` explains pairing. If the field test (T4.7) shows this
  hurting, the fix is one button and one small dialog.
- The host window still has no **Leave** button (Figure 3 shows New and Delete only). Still recorded, still
  locked by a test, still an open question.
