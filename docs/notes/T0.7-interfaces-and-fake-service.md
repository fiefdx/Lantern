# T0.7 — Interfaces and the fake chat service

**Task:** Define `IChatService`, `IRoomStore`, `IBtServer`, `IBtClient`, `IClientLink`; provide
`FakeChatService` (in-memory rooms and messages); rewire both windows to talk to `IChatService`
instead of hard-coded demo data.

**Result:** Both windows now run entirely off an `IChatService`. Nothing in `UI/` references
`Transport/`, a socket, or a hard-coded room. 33 tests pass, 0 warnings.

## What was added

### `Domain/` (completed here because the interfaces name these types)

| File | Notes |
| --- | --- |
| `MessageKind.cs` | `TEXT`, `PICTURE`, `FILE`, `JOIN_LEAVE_NOTICE` — also the discriminator the wire layer will use to pick a frame type (T1.3). |
| `Message.cs` | Abstract base: `Id`, `SenderNickname`, `SentAt`, `RoomName`, `Kind`, abstract `Preview`. Immutable. `RoomName` travels with the message so one frame is self-describing. |
| `TextMessage.cs`, `SystemMessage.cs`, `PictureMessage.cs`, `FileMessage.cs` | The four subclasses. `SystemMessage` owns the wireframe wording (`"X - join this chat"`) as `Join`/`Leave`/`Kick` factories. `FileMessage` carries a `TransferId` that ties the announcement to its `FILE_META`/`FILE_CHUNK`/`FILE_DONE` frames — the bytes never travel inside the message. |
| `User.cs` | `ConnectionId` + `Nickname`. The id is the *connection*, not the person, so two people with the same nickname do not collide in the session tables. |
| `Room.cs` | `ObservableCollection<User> Members`, an in-memory transcript (`Append`/`Transcript`), `AddMember`/`RemoveMember`/`ClearMembers`, `MembersChanged` and `MessageAppended` events. All mutations go through one lock; `Transcript` hands out a snapshot. Only the name is ever persisted (F9). |
| `FileTransferJob.cs` | One in-flight transfer: `FileName` (name only, never a peer's path), `SizeBytes`, `BytesDone`, `Fraction`, `Progress`, `CancelTransfer()`. `AddBytes` reports progress so the UI can bind a progress bar (F8). |

### `Core/`

* `ServerEndpoint.cs` — record: `ServerName`, `DeviceAddress`, `ServiceId`, plus the `DisplayName`
  the startup list shows.
* `IChatService.cs` — the whole contract the UI is allowed to know: `Nickname`, `IsHost`, `Rooms`,
  `Members`, `StartAsync`, `ConnectAsync`, `CreateRoomAsync`, `RenameRoomAsync`, `DeleteRoomAsync`,
  `JoinRoomAsync`, `SendAsync`, `SendFileAsync`, `SaveReceivedFileAsync`, `ShutdownAsync` and the
  six events `MessageReceived`, `RoomsChanged`, `MembersChanged`, `IncomingFile`, `StatusChanged`,
  `ConnectionLost`. Matches `docs/umls/02-class-ui-and-services.puml`.
  `JoinRoomAsync(null)` means "leave": one method covers both, so a window can never be in two rooms.
* `FakeChatService.cs` — in-memory implementation seeded with the wireframe content (three rooms,
  three people in the first, two messages each side). Plus three hooks the demo and the tests use:
  `SimulateIncoming`, `SimulateIncomingFile`, `SimulateConnectionLost`.

### `Storage/IRoomStore.cs`, `Transport/{IBtServer,IBtClient,IClientLink}.cs`

Contracts only, no implementation yet (M2/M4). `IRoomStore` stores names and nothing else.
`IClientLink` exposes `Input`/`Output` streams, so the frame codec cannot care whether it sits on
RFCOMM, localhost TCP or a `MemoryStream` pair.

## What changed in `UI/`

* `ChatForm(IChatService service)` replaces `ChatForm(string nickname)`. The base form subscribes
  to all six service events in `BindService()` and rebuilds itself from `Service.Rooms` /
  `Service.Members`; the old `LoadDemoData()` in both subclasses is gone.
* Selecting a room → `JoinRoomAsync` → members list, transcript replay, and Send/Share/txtMessage
  become enabled. Deleting or losing the current room drops the window back to the welcome screen.
* `StartupForm` constructs a `FakeChatService` (`isHost: true` for the server button,
  `false` for join) and passes it in — the seam M2 will replace.
* Sending validates through `ValidationRules.MessageError` *and* the service, refuses to send with
  no room selected, and clears the box on success.
* Incoming file → `ConfirmDialog` naming sender, file and size → `SaveFileDialog` →
  `SaveReceivedFileAsync` (scenario 6).

## Decisions

1. **The domain types landed here, not in T1.1/T1.2.** `IChatService` is full of `Room`, `User`,
   `Message` and `FileTransferJob`, so the interfaces were unwritable without them. T1.1/T1.2
   shrink to completing the hierarchy (frame-type mapping) and adding unit tests — T1.5 absorbs
   what `FakeChatServiceTests` already covers.
2. **`ObservableCollection<T>` on the interface.** The windows are WinForms; rebinding a list by
   hand for every change is exactly the kind of code that goes stale. `RoomsChanged` /
   `MembersChanged` are kept as well because a *service* (M2) raises them after marshalling onto the
   UI thread, and a bulk "everything may have changed" nudge is cheaper than reasoning about deltas
   across a socket.
3. **Events fire on whatever thread mutated the service; `ChatForm.OnUi` marshals.** Every handler
   goes through one guard: `IsHandleCreated && InvokeRequired` → `BeginInvoke`, otherwise run
   inline. Checking `InvokeRequired` alone is not enough — it forces handle creation — and requiring
   a handle made the service events invisible to the window tests, which never show a form.
4. **The sender renders its own message; the service does not echo it.** `SendAsync` records and
   forwards; only *inbound* traffic raises `MessageReceived`. That mirrors the wire protocol (no
   echo frames) and keeps the transcript from doubling up.
5. **Refusals are `InvalidOperationException`, surfaced in the status bar.** Duplicate room names,
   renaming as a client, over-long messages. `ChatForm.RunAsync` catches them and writes to
   `lblStatus`, so a refused action never reaches the WinForms message loop as an exception.
6. **`GlobalUsings.cs` in both projects: `global using Message = Lantern.Domain.Message;`**
   `System.Windows.Forms.Message` (the window-message struct) is in scope in every WinForms file, so
   an unqualified `Message` is CS0104. The alias is one line per project and keeps 20 files free of
   qualifiers.

## Follow-ups

* `SendFileAsync(string path)` on the interface is not exercised by the UI yet — `ChatForm` builds
  the `FileMessage` itself so the transcript updates immediately. M3 decides whether the service
  returns the message it announced.
* Room rename is on the Edit menu (F3) only; the wireframes show no rename button.
* The five-second "sending…" rule (scenario 4) belongs to the real service in M3, where sends can
  actually block.
