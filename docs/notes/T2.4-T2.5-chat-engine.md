# T2.4 / T2.5 — the chat engine over loopback

Two classes you can talk about without mentioning Bluetooth: `ChatServer` (the host process) and
`ChatClient` (everybody else). Between them, the frame types from T2.1 finally mean something.

## Who a member is: `IParticipant`

The person hosting has to be able to chat too, and the tempting shortcut — special-case the host in
`Join`, `Broadcast` and the member list — produces three copies of every rule. Instead the server
knows one thing about a member: it has a `ConnectionId`, a `Nickname`, and a `Receive(Frame)` that
must not block.

- `ChatServerSession` implements it over a socket (one connected client).
- `LocalParticipant` implements it in process (the host's own window), delivering frames as an event.

So `Room.Members` holds ids, `Broadcast` looks ids up in one dictionary, and the host is a member like
any other. `HostChatService` in T2.7 is the only thing that connects the host's window to a
`LocalParticipant`.

## Every decision is synchronous

A frame arrives on connection A's read loop; the server must decide what happens to connections B and
C. If that decision could await, a slow client would hold up the room and a half-applied join would be
visible to everyone.

So `Join`, `SendText`, `Unregister` and the rest take the lock, mutate rooms, release it, then hand
frames to `Receive`, which writes into a per-session `Channel<Frame>` and returns. Each session's
writer task drains its own queue. One consequence worth naming: the queue is unbounded, so a client
that stops reading cannot stall a room — it can only grow its own memory. T5.3 bounds it when file
chunks arrive, because then one client *can* produce frames faster than a link delivers them.

## Three rules that are easy to get wrong

**Nobody is echoed to themselves.** `SendText` broadcasts to the room except the sender; the sender
renders its own line locally. That is the rule `FakeChatService` already established, and it holds for
the host's window too — `LocalParticipant` gets no copy of what it said.

**The nickname comes from the handshake, not from the message.** A `TEXT` frame carries a nickname, and
`SendText` ignores it, stamping the identity that `HELLO` established. Without this, any client could
put words in anyone's mouth. `AFrameClaimingSomeoneElsesNameIsNotBelieved` is the test for that.

**Leaving a room is `JOIN_ROOM` with an empty name**, so one code path covers moving, joining and
leaving, and a member cannot be in two rooms by construction.

## Snapshots instead of live collections

`IChatService.Rooms` and `.Members` used to be `ObservableCollection<T>`. On a real client those lists
are rewritten by a background read loop, and a window bound to them could enumerate mid-update. The
interface now returns `IReadOnlyList<T>` snapshots plus the existing `RoomsChanged` /
`MembersChanged` events — which is how `ChatForm` was written anyway.

## Two things the tests found

`AMemberCanLeaveWithoutDisconnecting` failed intermittently, and the two causes were worth fixing in
different places:

1. **Product** (`ChatClient.ApplyMemberList`): a member list was treated as "which room am I in" only
   when it named one. A stale list for the room you just left — still in flight when you left — put
   you back inside it. The list now names the room it describes including the empty list that says
   "nobody is anywhere".
2. **Test**: waiting on the *host's* room before asserting on the *client's* view. The host applies a
   change before the frame announcing it arrives, so the test now waits on the client's own state.
   `Watch.UntilAsync` exists for exactly this, and every `Task.Delay` left in the file is a deliberate
   "give the wrong thing a chance to show up" pause, not a sleep.

Raw-socket tests also have to skip the frames a host sends unasked (`HELLO_ACK`, `ROOM_LIST`) before
the one they are waiting for — `ReadRawAsync(link, FrameType.ERROR)`.

## What is deliberately not here yet

- No server-side transcript: rooms on the host do not remember history, so a client that joins
  mid-conversation sees what arrives from then on. Re-entering a room replays the *local* copy.
- `PICTURE`, `FILE_META`, `FILE_CHUNK`, `FILE_DONE` are answered with `ERROR` — M5 opens them up.
- No protocol version negotiation; two different builds fail as a frame error rather than a clean
  "please upgrade". Same-build-only is fine for the demo and is listed as a known limitation.
