# T0.3 — NuGet packages & the `System.IO.Ports` vs 32feet.NET decision

## Packages added

| Package | Version | Why |
|:--|:--|:--|
| `InTheHand.Net.Bluetooth` | 4.2.5 | 32feet.NET — RFCOMM sockets (`BluetoothListener<T>` / `BluetoothClient`), service registration and discovery. Needed from **M4**. |
| *(none)* for JSON | — | `System.Text.Json` ships in the .NET 10 runtime. |
| *(none)* for UI | — | WinForms ships via `UseWindowsForms`. |
| `xunit`, `Microsoft.NET.Test.Sdk`, `xunit.runner.visualstudio` | 2.9.3 / 17.14.1 / 3.1.1 | test project. |

## The decision

The proposal assumed we might use "the built-in `System.IO.Ports` classes
(`BluetoothListener` and `BluetoothClient`)". We verified this on the actual SDK
(`dotnet 10.0.401`, `net10.0-windows`):

```text
error CS0234: type or namespace 'BluetoothListener' does not exist in 'System.Net.Sockets'
error CS0234: type or namespace 'BluetoothClient'   does not exist in 'System.Net.Sockets'
```

Findings:

1. **`BluetoothListener` / `BluetoothClient` are not in .NET 10 at all.** They only
   ever existed in *.NET Framework* 4.x (`System.Net.Sockets`), and were never
   ported to .NET Core / .NET 5+. There is nothing to "try first".
2. **`System.IO.Ports` is not a Bluetooth API.** It only exposes `SerialPort`. It
   *can* be used with Bluetooth indirectly — pair the remote device, let Windows
   create a COM-port binding, then read/write that `SerialPort`. That would mean:
   manual per-machine COM-port setup, hardcoded port numbers, no service GUID, and
   no way to enumerate peers. Not acceptable for a discovery-based app.
3. **32feet.NET 4.2.5 builds cleanly on `net10.0-windows`** and gives us exactly
   the .NET-Framework-shaped API (`InTheHand.Net.Sockets.BluetoothListener`,
   `BluetoothClient`, `Guid` service IDs, `BluetoothClient.Discover()`).

**Decision:** adopt 32feet.NET as the *only* Bluetooth transport; drop the
`System.IO.Ports` idea. It is referenced by `src/Lantern` but used **only** from
`Transport/BtRfcomm*.cs` (M4) so the rest of the code base never sees the type.

## Mitigation / fallback

Because hardware Bluetooth is the highest-risk item, the chat engine is developed
and demoed over a **loopback TCP transport** (**M2**) behind the same
`IBtServer` / `IBtClient` / `IClientLink` interfaces. If M4 slips, the loopback
build is still a complete, demoable product.
