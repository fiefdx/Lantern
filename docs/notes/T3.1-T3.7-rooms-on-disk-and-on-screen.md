# M3 — rooms on disk and on screen (T3.1 – T3.7)

M2 proved messages move. M3 makes the thing they move *inside* survive: the room list is a file the
host owns, it is edited from the host's window, and every window on the network follows the edits
without being asked.

Exit criterion: *rooms survive a restart; the live room list updates.*

---

## T3.1 — the file (`Storage/JsonRoomStore.cs`)

One file, `%LOCALAPPDATA%\Lantern\rooms.json`, per user, so two students on one lab machine do not
overwrite each other's rooms.

```json
{
  "version": 1,
  "rooms": [ { "name": "Room 1" }, { "name": "Garden" } ]
}
```

Decisions worth their salt:

- **Rooms are names, and nothing else.** Members and transcripts are not written. Membership is a
  property of who is connected *right now*; a room that remembered people who are not there would
  show a member list nobody can act on. A room reopened is empty (test: `AReopenedRoomHasNobodyInItAndNothingToRead`).
- **A missing or unusable file is the default rooms, never an exception** (F9). Junk, a bare `{}`, an
  array of numbers: `Load()` returns Room 1 / Room 2 / Room 3. `IRoomStore` therefore reports failure
  as an event (`SaveFailed`) instead of throwing — a chat that cannot save must still chat.
- **`{"rooms": []}` means no rooms, and stays that way.** Not the same case as junk: a host who deleted
  every room has to be able to *leave it deleted*, or F5 is a lie. The distinction in code is between
  "no entries at all" and "entries that all turned out to be useless".
- **A hand-edited file is expected** (F9 is checked by opening the file in Notepad), so a bare array of
  names — `["Room 1", "Garden"]` — is also read.
- **Names are normalised and de-duplicated on the way in**, case-insensitively, because joins match
  names case-insensitively too. `garden` and `Garden` in one file would otherwise produce two rooms
  that nobody can enter unambiguously.
- **Writes are atomic**: `rooms.json.tmp` then `File.Move(overwrite: true)`. A power cut mid-save leaves
  the previous file intact rather than a half-written one, which is exactly the case F9 is about.
- Two saves at once do not interleave (`TwoSavesAtOnceDoNotInterleave`).

## T3.2 — the server writes to it

`ChatServer` takes an `IRoomStore?`. Given one, the rooms come **from the file** and the `roomNames`
argument is ignored; given none, the code-supplied list still works (which is how most tests run).

- A save is queued after every CRUD, not instead of the broadcast — the UI never waits for the disk.
- Saves are **chained** (`await the previous one, then write this snapshot`), so the file ends up holding
  the *last* change rather than whichever write finished last.
- `StopAsync()` flushes pending saves (5s ceiling): a room created a second before File ▸ Quit is there
  on the next start (`AChangeMadeImmediatelyBeforeQuittingIsStillThereAfterwards`).
- A store that refuses to write is reported in the host's status bar and does not stop the chat
  (`AStoreThatRefusesToWriteDoesNotStopTheChat`, `AStoreThatThrowsIsReportedAndNotRethrown`).

## T3.3 — CRUD, and what a delete does to a person

`TryCreateRoom` / `TryRenameRoom` / `TryDeleteRoom` on the server; `CreateRoomAsync` etc. on
`IChatService` throw for a client (`AClientCannotEditRooms`) — the host owns the rooms.

Deleting a room that has people in it is the interesting one. Nobody is left pointing at a room that no
longer exists: everybody inside is put nowhere and the room tells them why before it goes —

> `Room 2 - closed by the host.`

— and the client's `CurrentRoomName` becomes null while the connection stays open, so it can join
another room without reconnecting (`DeletingARoomTellsThePeopleInsideAndPutsThemNowhere`). A rename
keeps the people inside, because names identify rooms and the membership is the room (`ARenameKeepsWhoeverWasInside`).

## T3.4 / T3.5 — the two windows, and the seam that made them testable

The buttons were wired since T0.5 and behaved; what they never had was a test, because every one of
them opens a modal, and a modal blocks a test forever. Each form now keeps its asking in one
overridable method:

| where | method | asks |
| --- | --- | --- |
| `HostForm` | `AskForRoomName` | the name, for New and Rename |
| `HostForm` | `ConfirmDeleteRoom` | "delete this room, and everybody inside gets put out?" |
| `HostForm` | `ConfirmQuit` | "everyone is connected to this window" |
| `ClientForm` | `ConfirmLeaveRoom` | "leave this room?" |

Handlers, wording and dialog classes are unchanged; a test subclass answers instead of a person.
`RoomManagementUiTests` then runs scenario 3 at window level, including two guard paths worth having
explicitly: Delete with nothing selected says so rather than guessing (guessing would delete whichever
room happened to be first), and a rename to a taken name is refused.

The client window stays read-only about rooms: it has no New and no Delete (asserted), it joins and
switches by clicking (one room at a time, F6), and Leave goes through the confirm.

`FakeChatService.SimulateRoomClosed` was added for the last case: a client does not edit rooms, so to
show a window what its host did, the fake has to be able to *have it happen to it*. Without that, the
case where the room you are standing in disappears underneath you has no test at the UI level — which
is precisely the case a user hits first.

**Two things learned about testing WinForms here**, both recorded because they cost time:
- `Button.PerformClick()` does nothing until the form has been shown: it goes through `CanSelect`,
  which is false while the window has no handle. Hence `form.Show()` in these tests.
- The status bar label is a `ToolStripStatusLabel`, i.e. a component in `statusStrip.Items`, not a
  control in `Controls` — `Controls.Find` will not return it.

## The window is the quit button — found by writing the manual check before automating it

The M3 checklist (`docs/testing/m3-manual-checklist.md`) was written out in prose first, and two of its
lines described things the code did not actually do:

1. **File ▸ Quit asked the host "are you sure"; the ✕ on the title bar did not.** Closing a host window
   disconnects everybody, so a keystroke was an escape hatch out of that question. The asking moved from
   `HostForm.OnQuitRequested` into `ChatForm.OnFormClosing`, which is on the way whether the user chose
   the menu, the ✕ or Alt+F4.
2. **`ChatForm.OnFormClosed` started the service shutdown and walked away** (`_ = Service.ShutdownAsync()`).
   Nothing waited for it, so a room created or renamed a moment earlier could still be on its way to
   `rooms.json` when the process ended — T3.2 flushes on `StopAsync`, but only for a caller who waits.
   The room comes back on the next start, and the only way to notice is to quit and look. The shutdown is
   now awaited, bounded (15s, above the server's own 5s ceiling), and deliberately started with
   `Task.Run`: awaiting on the closing thread would need the message loop that is itself on its way out,
   and blocking that thread directly would deadlock against the same loop.

Both are tested, and each test failed before the fix was written — which is the only reason to believe it
fixes anything. `ClosingTheHostWindowWritesWhatItPromisedBeforeTheProcessGoesAway` uses a store that
writes slowly, so a close that does not wait is caught not waiting: swap the wait back for the
fire-and-forget and it fails in a second with the file still unwritten.

For whoever writes more window tests later: **a plain `HostForm` in a test has to be given an answer to
the quit question.** A modal nobody is there to answer sits there until `Sta.Run`'s 30-second join gives
up, and the failure looks like an unrelated assertion.

## T3.6 — ROOM_LIST, and why a whole list

Any room change makes the server send the entire room list to every client. Not a delta: a client that
missed one frame while reconnecting would otherwise be permanently wrong about what rooms exist, and a
list of a dozen names is a few bytes. The same frame is sent on connect, which is how a client that
joined before the host created anything still learns about it
(`EveryClientFollowsTheHostsRoomListLive`, `AConnectedClientSeesTheRoomsTheHostOpened`).

The same reasoning covers membership: `MEMBER_LIST` for the *empty* name is authoritative and means
"you are in no room", which is what carries an eviction (T3.3) and a Leave to the client's own window.

## T3.7 — how the milestone is checked

| requirement | where |
| --- | --- |
| rooms survive a restart | `ARoomDeletedByTheHostStaysDeletedAfterARestart`, `ARoomListSurvivesARestart` |
| corrupt / missing file | `AFileThatIsNotARoomListIsTheDefaultRooms`, `AMissingFileIsTheDefaultRoomsRatherThanAFailure` |
| duplicate name refused | `TheHostCannotHaveTwoRoomsWithTheSameName`, `TwoSpellingsOfTheSameRoomBecomeOneRoom`, `RenamingToANameAlreadyTakenIsRefused` |
| kicked from a deleted room | `DeletingARoomTellsThePeopleInsideAndPutsThemNowhere`, `WhenTheHostClosesTheRoomTheWindowEndsUpStandingNowhere` |
| live room list | `EveryClientFollowsTheHostsRoomListLive` |
| scenario 3 in clicks | `RoomManagementUiTests` (11 tests) |

By hand: `docs/testing/m3-manual-checklist.md`, 20 steps — start a host, rename a room and create one,
quit by each of the three ways, start again, and edit `rooms.json` in Notepad, which is how F9 itself
asks to be checked.

## Loose ends carried into M4+

1. **The host's window has no Leave.** Figure 3 has New and Delete only, and a test asserts the host
   window has no `btnLeave`, so this is deliberate — but it means "I am leaving this room" can only be
   demonstrated from a client window; a host either moves to another room or quits. Worth one question
   to the marker before M6 polish.
2. **Whole-file saves are fine at this size.** If rooms grew to thousands, or transcripts were ever
   persisted, the atomic-whole-file design wants revisiting.
3. **One observed flake.** In ~10 runs of the 213-test suite a single failure appeared once and has not
   reproduced in the nine runs since, in a suite that binds fixed loopback ports (43797–43804); a
   lingering socket from the previous run is the prime suspect. Noted rather than papered over; M6 QA
   should run the suite several times on a clean machine before claiming stability.
