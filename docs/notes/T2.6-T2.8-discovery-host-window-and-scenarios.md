# T2.6 – T2.8 — finding a chat, hosting a window, and proving the whole path

Three tasks that turn "the engine works" into "the program works": discovery (`ServerBrowser`), the
host's own window service (`HostChatService`), and the scenario suite that runs the use-case document
against real sockets.

## Discovery can name an address, not a person (T2.6)

`ServerBrowser.DiscoverAsync` probes the loopback port range in parallel and returns what answered.
What answers is a TCP port, and a port does not introduce itself, so a discovered entry is called
"Lantern on port 43797". The real name arrives in `HELLO_ACK`: `FrameHeader.ServerName` was added, and
`ChatClient` adopts it into its `Endpoint` after the handshake.

That split is why the two are separate properties rather than one optimistic guess. A startup window
that displayed "Kitchen Table" while scanning would be showing something it had not been told. The
test for the split is in `Scenario1And2...`: the discovered name contains the port, and only after
connecting does the window know it joined "Kitchen Table".

`TryParseAddress` accepts `host`, `host:port` and a bare hostname — typing an address is the fallback
when discovery finds nothing, which on Bluetooth before M4 is the normal case.

## The host's window is a client of its own server (T2.7)

`ChatServer` is deliberately **not** an `IChatService`. The window belongs to the person hosting is
built out of `HostChatService`, which wraps the server plus a `LocalParticipant`, so the host appears
in member lists, gets notices, and cannot speak in a room it has not joined — the same constraints as
everyone else, from the same code.

Both `ChatClient` and `HostChatService` need to turn frames into rooms, transcripts and member lists.
That mapping has subtleties in it (an empty member list is authoritative; your own room is what the
server says, not what you asked for), so it lives in one place: `ClientState`, and each service is the
transport plus that state.

Two behaviours were settled while wiring the windows:

- **A message about a room you are not in is not drawn.** `ChatForm.ShowIncoming` filters by current
  room, so a notice about a room the user just left, or one the host closed, does not scribble over
  the conversation on screen.
- **Closing the window is File → Quit.** `ChatForm.OnFormClosed` calls `ShutdownAsync()`, because a
  chat still running behind a closed window is a bug the user cannot see or stop.

> **Amended in v1.0.3.** The stopping is still started there, and still for that reason. What changed is
> where it is *waited on*, and what the window is allowed to do afterwards: closing a chat window now
> returns to the startup window instead of ending the program, and the shutdown is handed over rather than
> blocked on. See [closing-a-chat-window.md](closing-a-chat-window.md).

## What the scenario suite found (T2.8)

`EndToEndScenarioTests` builds a host exactly the way `StartupForm` does — transport, server,
`HostChatService` — and clients exactly the way the same form does, discovery included. Four things
came out of writing it, and only the first is about the product.

**1. A transcript is arrival-ordered, and two windows can disagree about order (F6).** When Cara and
the host both send, each window puts its own line down at the moment of sending and the other's when
it arrives, so Cara's history can read "mine, theirs" while the host's reads "theirs, mine". Sorting by
the sender's timestamp would not fix it: two machines do not agree what time it is, and Bluetooth
peers have no shared clock. So the invariant the test asserts is that every window holds the **same
messages** (ids, not just previews) and that a window shows its own lines in the order it wrote them.
That is what desktop chat apps do. It is a known, deliberate property of F6 rather than a bug, and
worth repeating to whoever writes the transcript view in M4.

**2. A join that was written is not a join that was applied.** `JoinRoomAsync` completes when the frame
is on the wire. The first draft sent a message immediately afterwards, and the server — correctly —
delivered it to a room the sender had not been put in yet, so it went to nobody:

```
SendText room=Room 2 from=host-local members=[host-local]     <- the other join had not landed
Broadcast TEXT -> []
```

Every send in that file that depends on somebody else having arrived now waits for the arrival, via
`EveryoneSeesEveryone`. The barrier has to be a fact from the server (a member list, a notice), never
`CurrentRoomName`, which the client sets optimistically the moment it asks.

**3. A room's announcements stay inside the room.** A host standing in no room is told nothing about
joins and leaves, and a person who leaves is not told they left (`AnnounceLeave` excludes the leaver).
Both read odd until you say who would find them useful: the notice is for the people still there. The
tests assert the absence as well as the presence, so the next person to "fix" this has to decide on
purpose.

**4. The validator caught a bad test.** The helper used the chat's name as the host's nickname, so
"Kitchen Table host" (18 characters) hit the 16-character limit from F1. They are different things:
the name of a chat is not capped, the nickname of a person is.

## A window that throws used to be able to end a chat

The investigation above ended with frames queued, written, and a connection reporting itself connected
while nothing arrived. That particular case was a missing barrier in a test, but it exposed a real hole
in the product: events are delivered **on** the thing that raises them.

- `ChatClient` delivers `MessageReceived` from its read loop. A handler that throws — a form whose
  handle has just been destroyed throws `InvalidOperationException` or `ObjectDisposedException` the
  moment it is touched — ended the loop. The socket stayed open, `IsConnected` stayed true, and the
  user got a chat that received nothing ever again, with nothing on screen to explain it.
- `LocalParticipant` delivers the host's window's frames synchronously, from inside the server's own
  code. So a throwing handler in the host's window could unwind `Broadcast`, or `Join` halfway through a
  membership change.

Now every event in `Core` is raised through `Dispatch.Safe`, which discards an exception thrown by a
subscriber and, where there is a status line to write on, reports that something could not be shown.
The rule is narrow on purpose:

- **state first, then notify.** The frame's effect on rooms, transcripts and member lists is applied
  before any handler runs, so swallowing a handler cannot leave a room half-populated.
- **delivery only.** Nothing that the engine itself depends on is inside that `try`.
- `FakeChatService` is deliberately **not** wrapped. It delivers on the caller's own thread, so a throw
  there is the test's own bug and should be seen. There is a comment on `SimulateIncoming` saying so,
  because the next person will otherwise "fix" it.

Both guards are pinned by tests that fail when the guard is removed —
`AWindowThatThrowsWhileListeningDoesNotEndTheConnection` and `AThrowingHostWindowLeavesTheServerIntact`
— checked by deleting the guard and watching each test time out. A test that passes with and without the
fix it is supposed to be testing is worse than no test, because it argues against the bug being fixed.

## How a stalled or bad peer behaves

Worth stating because M5 (files) will stress it: a client that stops reading grows its own channel and
nobody else's; a frame that cannot be parsed ends only that connection; an `ERROR` frame is a message to
the user, not a disconnect.

## Not here yet

- No server-side transcript, so joining mid-conversation shows what arrives from then on (M3's room
  persistence is where history starts).
- Discovery is a port scan of a fixed range. Bluetooth discovery (T4.4) replaces the probe, not the
  `ServerEndpoint` type.
- `ServerBrowser` reports no device name, only host and port, because loopback has no device.
