# T5.3 — a file across the room, in pieces

Milestone M5 · task T5.3 · area Net

## What the task asked for

Send a file of any size: announce it, stream it in chunks, reassemble it on the other side. No
corruption, and no `OutOfMemoryException` on a large file.

## The frames

Three of the thirteen, plus one invented here:

| Frame | Carries | Direction |
| --- | --- | --- |
| `FILE_META` | message id, transfer id, room, sender, file name, size in bytes | sender → room |
| `FILE_CHUNK` | transfer id, sequence number, up to 8192 bytes | sender → room |
| `FILE_DONE` | transfer id | sender → room |
| `FILE_CANCEL` | transfer id | both ways |

`FILE_CANCEL` is the one that was not in the original wire table. META, CHUNK and DONE only carry
bytes one way, so there was no way to tell a sender to stop: a receiver who declined a 2 GB file, or
whose machine stopped taking bytes, would leave the sender pushing the whole file into a socket
nobody is reading. A protocol needs a word in both directions.

Sequence numbers are the receiver's only protection against a hole. `FILE_CHUNK` carries the number
it was written with; a receiver that sees 0, 1, 3 knows the second half of the file is missing and
says so rather than quietly saving a file with a piece cut out.

## Where the bytes live while they move

**On disk, not in memory.** The receiver writes each chunk to
`%LOCALAPPDATA%\Lantern\incoming\{transfer-id}-{receiver-id}.part` as it arrives. Accepting a file
means moving that spool to wherever the person asked for; declining deletes it. A 4 GB file costs the
same memory as a 4 KB one, which is the whole reason for the spool.

The `{receiver-id}` half of the name is not decoration. Two Lantern windows on one laptop share the
incoming folder — the host is a member of its own room, so a file sent by a client is received by the
host window *and* by every other client, in one process during a test and in one household in real
life. Named by transfer id alone, the second receiver was correctly told that the file it was
holding belonged to somebody else.

The sender never buffers either: it reads 8 KiB, writes 8 KiB, repeats.

## Flow control, which is where the week went

A host relays to several connections at once, and a Bluetooth link is slow. Without pacing, a fast
sender plus two slow receivers means the bytes pile up in the host's outboxes — memory that grows at
whatever rate the sender can read, until it stops being memory.

Each transfer gets its own bounded queue (8 frames) and a pump task that hands frames to the room:

```
sender's read loop ──▶ Channel<Frame>(8) ──▶ pump ──▶ each recipient's outbox
                              ▲                  │
                              │                  ▼
                       producer waits      "is anybody in this room
                                            holding more than 64 KiB
                                            of this file? if so, wait"
```

The producer blocks when the queue is full, so back-pressure reaches the sender instead of stopping
at the host. The watermark is per recipient and per transfer: 8 chunks × 8 KiB. A recipient that
cannot drain it within `FileFlowTimeout` (20 s) gets the transfer stopped for everybody, and told
why — a room where half the people have a file and half do not is worse than a room where nobody
does.

One decline is not a stop for all. If one of three people declines, that connection is marked
declined, the other two carry on, and the sender is only told when the last recipient has gone.

## The three bugs this found

All three were found by writing the test first and being annoyed afterwards.

**1 · The watermark never let go.** `ChatServerSession` counts the bytes sitting in its outbox so the
pump can decide whether a recipient is behind. It counted them going in. It never counted them coming
out. So after eight chunks every recipient looked permanently 64 KiB behind, every transfer stalled at
exactly that point, and the failure looked like a network problem from the outside. An
`Interlocked.Add(ref queuedBytes, -frame.Body.Length)` after the flush, and only after it: a counter
that decrements before the bytes have gone is the same lie in the other direction.

**2 · A remote sender's "done" was never relayed.** When the host sends a file, `FileSending` writes
META, chunks and DONE into the relay. When a *client* sends one, the host's `HandleAsync` handles
each frame — and the `FILE_DONE` case completed the queue and waited for the pump without ever putting
the DONE frame in it. The bytes arrived, the receiver's progress reached 100%, and no window ever
learned the file was finished. It only showed in the client-sends tests, because the host-sends path
takes the other branch.

**3 · Two receivers, one spool** — the shared-name bug described above.

## What is deliberately not here

* **Resuming.** A stopped transfer stays stopped. Renegotiating a partial file needs a second
  protocol and nobody asked for a download manager.
* **Encryption and authentication.** Same as every other frame on this wire (M6 note).
* **A per-transfer progress *event*.** The job is the progress: the window reads `BytesDone` and
  `Fraction` off it. An event per chunk is 12 000 events for a 100 MB file.
* **Virus scanning, or any content inspection.** Noted in the manual checklist instead.
