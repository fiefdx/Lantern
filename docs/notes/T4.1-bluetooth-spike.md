# T4.1 — Bluetooth spike: what this machine's stack will and will not do

**Question:** can two Windows laptops run Lantern over real RFCOMM, using 32feet.NET
(`InTheHand.Net.Bluetooth` 4.2.5, adopted in T0.3), with the wire protocol and the rest of the code
untouched?

**Method:** `tools/BtSpike`, a console probe that uses the application's own
`LanternProtocol.ServiceId` and `Lantern.FrameCodec` — a spike that invented its own GUID or framing
would prove that the radio works, which was never the doubtful part. Everything quoted below was
printed by running it on the development machine (Intel radio, Windows 11, .NET 10 SDK 10.0.401).

```
dotnet run --project tools/BtSpike -- api | radio | paired | scan [s] | host [s] | raw <address> [guid] | probe <address> [s] | pair <pin> <address>
```

## Answers, with the evidence

| question | answer | evidence |
| --- | --- | --- |
| Is there an adapter to talk to? | yes, and it reports itself | `radio` → `BluetoothRadio.Default`: `Name = DESKTOP-G0ARUQV`, `LocalAddress = F8E4E3F9603B`, `Manufacturer = Intel`, `Mode = Connectable` |
| Can an app **publish a private service GUID** and accept RFCOMM connections? | **yes** | `host` → `listening for c1a5ee70-…-4c2b6f9d1a01 as "Lantern" (active: True)`, and `Stop()` removed the record cleanly |
| Does inquiry work? | yes, slowly, and it finds little | `scan 12` → `answered: 1` (an LG webOS TV). Most devices are not discoverable most of the time |
| Can we list devices the machine already trusts? | yes | `paired` → 5 devices, with `DeviceAddress`, `DeviceName`, `ClassOfDevice` |
| Is there an API for "**which machines host the Lantern service**"? | **no** | `api` → `BluetoothServiceCatalog: absent`, `BluetoothService: absent`, `ServiceDiscovery: absent` |
| What does an outgoing connect do when the peer is not hosting Lantern? | it really tries, then times out | `raw 34885DBDCC01` → `SocketException (socket code 10060)` after **≈5 s**; same for a paired phone, same for an address that does not exist |
| What if the address is one the stack refuses? | a different, distinguishable code | `raw A0D365349927` (this machine's own entry in its own paired list) → `SocketException (socket code 10049)` immediately |
| Can one machine be both ends? | **no** | `probe` against its own address fails; two radios on one box are not selectable — the library exposes `BluetoothRadio.Default` only, no adapter choice |
| Is there a pairing API? | yes | `BluetoothSecurity.PairRequest(device, pin[, requireMitmProtection])`, `RemoveDevice(device)` |
| Can the wire protocol ride on the RFCOMM stream? | nothing to show yet | `host` accepted nothing (no second machine). `FrameCodec` reads/writes a plain `Stream`, and `BluetoothClient.GetStream()` is one — but that is an inference, not a result, until T4.7 |

## Two traps the spike found in the library

1. **`BluetoothClient.ConnectAsync(address, service)` is not trustworthy here.** The same endpoint that
   takes ≈5 s and reports a timeout through the synchronous `Connect(new BluetoothEndPoint(address, service, -1))`
   comes back from `ConnectAsync` **immediately** with `SocketException 10022` ("invalid argument") —
   including against a paired, reachable device. So `BtRfcommClient` will call the **synchronous**
   `Connect` on a thread-pool thread and put its own timeout around it (`Task.WhenAny`), rather than
   trust an async overload that never reaches the stack. A connect that cannot be told apart from a bug
   is worse than a blocking call we control.
2. **`AddressFamily.Bluetooth` does not exist in .NET 10** (`error CS0172`-class compile failures when
   the spike tried to build a raw socket; `Socket.OSSupports` never got a chance). 32feet uses its own
   socket wrapper. Consequence: no BCL-level `Socket` options, no `Select`, no `SetSocketOption` —
   timeouts and cancellation are entirely our business.

`BluetoothListener.AcceptBluetoothClientAsync()` and
`BluetoothClient.DiscoverDevicesAsync(CancellationToken)` **do** exist, which is convenient: accepting
and scanning can both be awaited and cancelled; only *connecting* has to be wrapped.

## Decisions taken from this

### D1 — keep loopback in the product, permanently

One machine cannot be both ends of a Bluetooth connection, and the automated suite must not need two
laptops and a willing human. `BtLoopbackServer`/`BtLoopbackClient` stay behind the same `IBtServer` /
`IBtClient` / `IClientLink` interfaces as `BtRfcommServer`/`BtRfcommClient`, and the transport stays
selectable at start-up. M4 replaces the transport, not the tests.

### D2 — discovery cannot be "search for the service", so it is "who is there, then try"

With no service-catalog API there are exactly two sources of candidate addresses:

- `PairedDevices` — the machines this one has been set up with. Cheap, instant, and honest.
- `DiscoverDevicesAsync` — an inquiry, which takes the whole timeout the caller allows and usually finds
  devices that are not running Lantern (the development machine found one TV in twelve seconds).

So **Scan lists candidates; joining is the probe.** The scan does not pretend to know who hosts Lantern
— it lists what it can see, marks which of them Lantern has talked to before, and the connect attempt is
what discovers the truth. The measured behaviour makes that tolerable: an absent service costs ≈5 s and
comes back with a code we can name in the status bar, and the user is the one who decides to try.

A second input stays available because the address is enough: **connect by address** (`ServerBrowser.TryParseAddress`,
extended to accept `F8E4E3F9603B` / `F8-E4-E3-F9-60-3B` / `f8e4e3f9603b`). If a scan finds nothing — the
usual case when the other laptop is not in limited-discoverable mode — typing the address from the other
machine's `BtSpike radio` output still works.

### D3 — pairing is a documented step, not a surprise

Windows will not silently open an RFCOMM connection to a stranger: on an unpaired device the connect
either fails or produces a prompt on both machines. Since the pairing question cannot be answered on one
machine, Lantern treats pairing as a **precondition of the field test, written down in advance**
(`docs/testing/bluetooth-pairing-how-to.md`), and the UI reports a connection failure with the address,
the code and a pointer to that page rather than "connection failed". If T4.7 shows that Windows can
connect without prior pairing on some stack, the how-to becomes optional — the reverse never is.

### D4 — service registration carries a name, and the name is the only human-readable thing available

`BluetoothListener.ServiceName = "Lantern"` is set on the host: it is what appears in the Windows
Bluetooth services panel when something goes wrong, so it is worth more than an unnamed record. What the
peer's *device name* is (`BluetoothDeviceInfo.DeviceName`) is filled in where the stack gives it —
the spike had to guard that call, because it sometimes refuses.

## What this spike cannot prove, and who has to

That two machines can pair, that a Lantern service on one is found and connected from the other, that
the frame codec survives an RFCOMM stream (MTU, partial writes, 8 KB chunks), and how long a real scan
takes in a room with real laptops. All four are **T4.7 — field test on 2–3 physical laptops**, which is
why `BtSpike host` and `BtSpike probe <address>` exist as separate commands: they isolate the transport
from the chat, so a failure in the field says "transport" or "Lantern" instead of "something".

## Loose ends

- `BluetoothRadio.Default` on this machine reported `LmpVersion = Version21`; a Bluetooth 5 radio should
  report higher. Probably a library quirk, possibly relevant to which features are usable. Recorded, not
  chased.
- The development machine's own address appeared in its own `PairedDevices`. Unexplained; harmless for
  Lantern (it is filtered out of candidate lists by comparing against the local address), and it is the
  reason `raw` was the only command that produced error 10049.
- `BtSpike` is a tool, not a product: no tests of its own (the suite covers what Lantern *ships*; the
  spike prints what it sees), and it is excluded from the release build.
